# 吃乎工作台：需求草案

状态：首版已在本地实现并通过自动化检查，尚未部署到社团服务器或完成真实用户验收。更新于 2026-09-24。开发任务与检查计划见 `vibecoding-plan.md`，实际验收进度见 `development-log.md`，样例映射见 `sample-analysis.md`。

## 目标与范围

按项目组织排期、参加确认、菜品认领、测评和照片、共同编辑、提醒和报销导出。成员以手机访问为主，组长可在电脑上集中管理，通常同时参与约 4–10 人。已知有两台 Ubuntu 服务器、已有域名和 HTTPS。配置按每台约 4 核 4GB 暂估，准确配置、磁盘和网络条件部署前核实。维护者熟悉 Python；首版采用共享编辑、评论与版本，提醒以站内待办为主。已检查 `sampal/` 中一份报销表及四张图片。

首版即支持一个测评项目包含 1 至多次到店活动。项目保存主题、成员、总体截稿时间和总稿；活动保存店铺、排期、名单、菜品、订单及费用。成员可仅参加其中部分活动；同一店铺可重复到店，每次活动仍有独立 ID。投票、确认、任务和费用不能按店名或项目总名单混用。一个活动可有多个档口和订单。

## 角色与入口

- 角色按项目分配：同一成员可在项目 A 当组长，在项目 B 当组员。
- 组长视图：进度概览、时间与名单、菜品任务、审稿、费用与导出、项目设置。
- 组员视图：我的待办、时间投票、参加确认、菜品认领、写测评、传照片、讨论。
- 组员可查看项目公共材料，默认可共同编辑刊发文案；个人原始投稿独立保留，其他人通过评论或建议反馈。每次保存留作者与版本。
- 组长可分配或转交任务、编辑正文、接受建议、退回、定稿、恢复历史版本。
- 票据及付款信息默认仅提交者和组长可查看。权限由服务端校验，不能只隐藏界面。
- 账号由管理员批量导入，关闭自行注册；用户可改资料和密码，稳定 UUID 不变。所有登录成员可在大厅加入未结束项目，邀请链接为可选入口。

## 项目进度

项目状态：筹备、进行中、待收尾、已归档。每次活动独立流转：草稿、投票中、待确认、待到店、已完成、已取消。取消活动后取消或转交对应待办，保留已有内容与费用历史。

内容流程：待认领 → 撰写/上传 → 待审核 → 待修改或已通过 → 已定稿。

费用流程：待提交 → 待核对 → 材料齐全 → 已导出 → 已报销。

内容与费用分别推进。导出文件不等于已报销，人数齐全不等于已确认参加。

## 时间收集与名单

- 组长选择日期范围、星期过滤、午餐/晚餐及各自时间，一键生成候选时段。
- 成员对每个时段选择能参加、待定、不能参加。未填写单独显示，不当成不能参加。
- 展示各时段人数和名单，推荐人数较多的时段，最终由组长确认。
- 确定时间后，成员必须再次确认参加或不参加，投票不自动转成报名。
- 支持确认截止时间、人数上限、候补、取消参加。
- 时间发生实质变化后，原确认标为需要重新确认，保留旧记录。
- 确认名单作为后续任务分配依据；退出者已有任务需明确转交或取消。
- 每次活动独立投票、确认。最终时间变更时提升排期版本，原确认需要重新确认；不影响同项目其他活动。显示及截止判断使用 Asia/Shanghai，数据库保存带时区时间。

## 菜单识别与认领

- 支持多张菜单截图，识别菜名、规格、价格、分类及原图来源。
- 识别结果进入预览校对页，缺失字段留空并提示，不编造菜名或价格。
- 允许合并重复项、拆分套餐、改名、手动补菜；重试识别不能重复创建任务。
- 区分菜单候选菜与实际点单菜，只为选中的实际菜品生成必需任务。
- 每道菜独立设置文案负责人和照片负责人，两者可由不同成员认领；可有协作者。
- 每项任务有负责人、截止时间、状态、审核意见；同时认领时只能有一个主负责人成功。
- 支持组长指派、转交、取消及调整需求，例如不要求每道菜都有独立照片。
- 改菜名保留原有 ID，不丢失测评、图片、评论和费用关联。
- 同一道菜可保留多位成员的独立评价，以及一份可共同编辑的刊发文案，避免抹掉不同观点。
- 套餐父项计费一次，子菜品分别认领但不重复加钱。二选一保存选项组，实际选择确认后才产生对应必交任务。纸巾、餐具等可作为费用项而不生成测评任务。
- 保存数量单位与价格语义，区分单价、小计和套餐价；识别缺失值留空。不得把行小计再次乘以数量。

## 测评、照片与协作

- 测评支持自由文案和可配置提示，例如口味、分量、价格、推荐理由；可暂存后提交。
- 图片支持批量上传、失败重试、原图保存、缩略图预览、作者及菜品绑定、挑选与排序。
- 上传成功与提交审核是两个状态；未完成上传不计入任务完成。
- 评论首版绑定菜品/文案卡片；段落定位评论可随后补充。
- 修改建议是独立记录，保存建议者、基于的版本、建议内容、接受/拒绝状态。
- 文案已变化时，旧建议需重新比较，不能覆盖当前正文。
- 基础协作支持共享访问、评论、修改建议、自动保存和版本检查；并发保存冲突时保留双方内容，不能最后写入者直接覆盖。
- 首版使用 Markdown 输入、预览和少量格式按钮；服务端清理渲染内容。无需实时字符同步、Yjs、WebSocket 或常驻 Node 编辑服务。
- 保存携带 `base_revision`，服务端条件更新；旧版本提交返回冲突与当前版本，保留本次草稿并展示比较，不静默覆盖。自动保存失败明确显示，不能只在浏览器显示“已保存”。
- 历史版本保存操作者、时间、原因、正文快照及版本关系。自动保存合并成合理检查点，提交、接受建议、定稿时保留明确版本。
- 恢复旧版本先预览，再生成当前新版本；不删除中间历史，恢复时同样检查当前 revision，避免覆盖刚提交的新稿。
- “撤销自己的输入”“恢复一份历史文稿”“接受别人的修改建议”是不同功能，不混用。
- 定稿后成员仍可提意见，正文需重新开启编辑；更改已审稿内容应重新进入待审核。
- 整篇推文按活动和菜品排序组合成项目总稿，支持共享编辑、评论及版本。源文案变化时提示总稿可能过期，不覆盖人工编辑。导出定稿 Markdown/可复制文稿与有序配图包，供秀米或小红书后续处理。

## 缺项提醒

- 依据确认名单及明确任务判断缺项：未投票、未确认、无人认领、缺文案、缺照片、待修改、缺票据。
- 未投票提醒面向被邀请成员；内容提醒面向实际负责人，避免提醒退出者和无此任务者。
- 首版以站内待办和到期提示为默认渠道，页面打开时可轻量刷新；关闭网页后不承诺主动送达。组长可一键复制催交摘要。
- 微信内打开网页不等于具备主动微信消息推送能力。暂不依赖普通微信群机器人或微信内浏览器的后台推送。
- 提供可复制的群提醒摘要，作为外部通知接入前或失败时的补充。
- 截止前提醒、到期提醒、逾期汇总给组长；设置频率上限和安静时段，完成即停止。
- 记录每次通知结果；按任务、提醒类型及时间窗口去重；发送前重新检查完成状态。
- 组长可延期、豁免、转交或按已收材料截稿；豁免和缺项不能伪装成正常完成。
- 已读不等于任务完成；改期、取消、退出和完成会更新待办。若以后已有 SMTP 或统一平台消息接口，再接一个可关闭的通知适配器，失败不影响站内提醒。

## 报销整理与导出

- 首版按 `sampal/小龙虾报销.xlsx` 固定模板实现，保留负责人、项目、数量、单价、备注、费用六列，店铺块小计和末尾总对接人/总费用。模板“项目”列映射店铺/费用分组，不是应用测评项目标题。原件只读，导出写新文件。
- 菜单、结账单、付款凭证、发票、退款记录分别保存，不互相替代。
- 菜单价格只作参考；费用总额来自核对后的实际支付及退款记录。
- 支持多人垫付、一单多次付款、优惠、退款和多张票据关联。
- OCR/多模态模型提取商户、日期、金额等作为待确认值；保留原图和人工修订记录。
- 以整数分或精确十进制计算金额，检查合计差异、缺凭证、疑似重复付款。
- 导出前展示费用清单、金额及缺项。缺项时可保存带提示的草稿，正式导出要求检查通过或组长明确记录例外。
- 导出内容：报销表格.xlsx、按凭证编号组织的原始证明文件、模板需要的图片汇编、材料索引。
- 表格行与附件使用同一凭证编号关联。原件完整保存；图片拼版或格式转换生成派生文件。
- 导出记录保存数据版本、模板版本、导出人、时间和文件，数据后来变化则提示重新导出。
- 隐藏在列表或视图中的财务文件仍须经过下载权限校验。
- 订单应付、实际净支出、拟报销金额分开保存；支持代付说明和差额核对。一笔付款可分配到多订单，但分配合计不得超过其可用净额；重复凭证只增加证据，不增加支出。付款人和表格负责人分别建模。
- 可按项目或选定活动导出。当前样表是文字金额、无公式、无内嵌图片；金额计算由 Python Decimal/整数分完成，模板显示层输出对应文本，证据另附原图与索引。
- 样表内部加总 550 + 122 + 437 + 258 = 1367 元。图片只覆盖部分款项；菜单与实付金额的差异必须展示待核对，不能假定凭证齐全。具体用例见 `sample-analysis.md`。

## 技术方案（按 Python 维护习惯调整）

- 应用：Python + Django 5.2 LTS 的当前受支持补丁版，模块化单体。页面使用 Django Templates + HTMX + 少量 JavaScript/CSS，移动端优先。初始化时核对兼容矩阵并锁定依赖。
- 数据库：PostgreSQL，负责项目、成员、任务、费用、权限及版本元数据。
- 文件：首版使用持久化目录与私有下载接口，文件元数据入库；后续可以切换 S3 兼容存储。
- 异步工作进程：数据库任务表 + Django 管理命令 worker，单 worker 起步；行锁领取、租约回收、重试及幂等。一个 cron/systemd timer 负责定时检查，重复执行也须去重，暂不额外引入 Redis。
- 评论、修改建议、业务版本在 Django 中独立建模，首版无需付费编辑器扩展。
- 菜单/凭证识别通过可替换适配层接入，失败时可人工录入。模型选择需用实际菜单和票据样本验证；不假定服务器具备本地模型推理能力。
- 应用运行期的报销导出使用 Python 固定模板生成器，优先验证 openpyxl 对当前简单模板的保真；原始样表不覆盖。使用样表及样例金额检查，再以 Excel/WPS 实际打开与打印预览验证。
- JSON 接口采用 Django REST Framework，路径 `/api/v1/`；页面与 API 复用业务服务层。
- Docker Compose 部署 Gunicorn Web、PostgreSQL 和单 worker，接入现有 HTTPS 反向代理。
- 测试采用 pytest/pytest-django 与真实 PostgreSQL，关键流程增加浏览器测试；认领锁和并发保存不能只用 SQLite 测试替代。

## 数据与未来平台集成

- 主要实体：Organization、User、ExternalIdentity；Project、ProjectMember、Visit、Venue；TimeOption、Vote、Attendance；MenuSource、MenuCandidate、ChoiceGroup、Dish、Assignment；Review、Revision、Comment、Suggestion、Asset；Order、OrderLine、Adjustment、Payment、PaymentAllocation、Refund、EvidenceLink、ExpenseClaim、ExportRun；Notification、AuditEvent、Job。
- 首版只启用一个社团，保留组织作用域及稳定 UUID，不先建设多租户 SaaS。所有子对象的活动/项目/组织关系在服务端一致校验。
- 初始账号用 Session 和 CSRF；预留 `provider + subject` 唯一的外部身份映射，将来按平台协议接 OIDC 等登录。不按同名昵称合并账号，不信任任意用户 ID 请求头。
- API 明确版本、权限、分页、错误格式和 OpenAPI 合同；未来平台通过接口接入，不直接操作本应用表。
- 业务规则放在服务层，由页面、API 和管理命令复用。文件通过 Django Storage 接口访问，避免把磁盘路径写死在业务中。
- 对接顺序：平台入口链接、统一登录、按需数据同步。主平台未建成不阻塞独立上线；通知/webhook 仅保留扩展边界。

## 两台服务器的初始安排

按 Ubuntu、每台约 4 核 4GB 的暂估配置，先采用 A 生产、B 构建/测试及备份恢复环境的部署方案。已有域名和 HTTPS，接入现有反向代理或确认其配置后新增站点；不覆盖现有服务。实际资源和网络条件部署前核实。

- A：Django Web、数据库、文件和单任务进程，首版无需实时协作服务。
- B：镜像构建、隔离的测试实例、数据库和文件的版本化备份，以及恢复演练。构建与测试设资源限制，必要时错开运行；备份和恢复任务优先保障。
- 测试实例不使用生产通知凭据，不向真实成员发测试提醒；备份文件对测试应用不可见。
- 两台机器不因此自动构成高可用；生产故障需要按恢复流程切换。
- 性能、磁盘和网络情况明确后再调整，备份保留历史，不只同步最新文件。
- 生产机运行预先构建的镜像；部署保留上一版镜像以便回退，数据库迁移需单独检查兼容性。
- 数据库及内部任务接口不直接暴露公网；按已有 HTTPS 入口转发网页，票据不放公开静态目录。
- 首版减少常驻服务数量，暂不引入 Redis 和自建对象存储服务；图片文件存入持久化目录，目录及数据库一起备份。
- 识别通过可替换的外部服务适配层实现，不按此内存配置安排本地大模型。服务商及数据发送范围接入前落实，支持人工录入。
- 图片缩略图和导出任务从低并发开始，配置文件大小限制、资源上限和失败重试。初始先限制为一个重任务同时执行，实测后调整。
- 容量验证以真实菜单、手机原图、多人编辑和导出样本为准，不将机器规格当作并发人数承诺。图片磁盘容量、备份容量及上传带宽需单独核实。

## 开发顺序与验收

1. 项目与人员：登录、项目角色、时段批量生成、投票、最终确认；验证改时间后需要重新确认。
2. 内容闭环：手动菜品卡、双任务认领、测评/照片、评论、建议、版本；验证两人同时认领和编辑不会静默丢数据。
3. 自动化：菜单识别、缺项检查、站内提醒；验证识别重试不重复建卡、重复检查不重复提醒、完成后停止。
4. 报销：实际样表、支付及票据关联、识别校对、导出；验证优惠退款、多付款人、重复票据和附件编号。
5. 发布前：项目及财务权限、手机上传失败恢复、数据库及原图恢复演练；用一场真实活动完成全流程试用。

以上是概要实现顺序；完整依赖、AI 执行提示、验收与检查见 `vibecoding-plan.md`。首版不做实时字符同步，外部通知不作为上线依赖。
