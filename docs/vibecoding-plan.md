# 吃乎工作台 Vibecoding 与检查计划

更新：2026-09-24。28 个工作包、80 个检查场景。本文件保留原始计划与检查口径；当前代码实施、已运行检查和待实测项见 [实施记录](development-log.md)。每个工作包均有依赖、AI 提示、交付物和验收。

## 使用方式

本文件保存范围与执行说明；随附 Excel 的“开发计划”和“检查清单”用于日常填写状态、负责人和证据。后续以 Excel 跟踪执行状态；若需求变动，先同步本文件和产品方案，再更新工作包。不要把计划表生成成功当作产品验收通过。

一次向编码 AI 下发一个工作包，复杂包可以按“模型与服务、可操作页面、验证”分成数轮；每轮仍须交付能复查的具体变化。按依赖推进，先人工录入跑通，再接识别和导出。无日历日期和工期承诺，避免将未经验证的估算当排期。

## 每轮通用提示词

> 你正在实现吃乎工作台。先读 docs/product-plan.md、docs/sample-analysis.md 和本计划中指定工作包。执行工作包【编号】，确认前置项已有验收证据；若缺失，先报告具体缺口。先检查现有代码和仓库规则，再列出本轮要改的文件、业务边界与必要迁移。使用 Python/Django、PostgreSQL、模板和 HTMX，页面与 API 复用服务层。首版支持一个项目多次到店，4–10 人，共享编辑、评论、版本和站内提醒。实现该工作包及其关联检查，保留原始样例，真实交易号和身份不进入公开测试、日志或代码。不可用假成功、硬编码样例金额或跳过失败测试凑验收。验证结束报告实现内容、实际执行的命令及结果、未执行项和原因，并附可复现的页面路径或输出文件。不要扩大到未排入本轮的功能。

## 每轮完成标准

1. 读当前代码与工作包，前置任务已验收；依赖失败时先解决依赖。
2. 实现业务规则和页面，表单/JSON/后台命令使用相同服务规则；必要的数据约束进数据库。
3. 针对金额、权限、并发、版本、附件与状态等风险执行相应测试，纯文字或视觉小改不堆重复测试。
4. 检查 diff 与迁移；确认没有凭证、密钥、临时文件或无关改动混入交付。
5. 验证主路径及指定异常路径。失败项修复后复测相关范围，未执行项标记原因，不以 mock 替代真实集成结果。
6. Excel 填状态和证据（提交哈希、测试报告、截图/导出文件、环境与日期）。只有达到验收标准才能设为“已验收”。有 Git 时每个验收工作包形成可回退提交。

建议命令基线（工程建立后使用实际路径）：

```text
uv run ruff check .
uv run ruff format --check .
uv run python manage.py check
uv run python manage.py makemigrations --check --dry-run
uv run pytest <本工作包对应测试路径>
# 涉及生产设置时，在隔离环境配置真实的生产设置模块后运行：
uv run python manage.py check --deploy --settings=<生产设置模块>
# 涉及页面时，另运行该工作包浏览器检查并保留结果。
```

这些是原始计划命令；当前工程的实际命令和结果以实施记录及 README 为准。初始化时锁定相容的 Python、Django 5.2 LTS 补丁及其他依赖；不得把占位参数原样当成通过的命令。
